# Use one Cloudflare Worker with Static Assets for free-first hosting

Deploy the desktop web interface and backend together as one Cloudflare Worker with Static Assets, and store the Player Directory, Queuing Directory, authentication/session data, and global upload lease in D1. Use the existing `badminton-youtube-uploader` Worker for production and a fixed Worker Preview named `staging`, with a separate APAC D1 database for each. To remain within Cloudflare's request-body limits while protecting the centralized YouTube token, the browser splits each video into smaller resumable chunks that the Worker relays to YouTube without persistently storing the file. Completed Game Upload metadata is not retained.

## Consequences

Worker code and React assets are built and deployed as one version, so there is no Pages project or Pages Functions deployment to coordinate. Production bindings live at the top level of `wrangler.jsonc`; Preview variables and D1 bindings are repeated under `previews` because they do not inherit production values. Preview secrets are independently installed with Wrangler's Preview secret commands. Staging and production share no D1 data, but temporarily use the same dedicated YouTube test channel and Destination Playlist with different shared passwords. The application depends on Cloudflare's platform limits and pricing, which can change. Chunk sizes must remain valid for both Cloudflare and YouTube, the design must tolerate retrying individual chunks, and deployment still incurs domain-registration cost after Phase 3 even if platform usage remains within free allowances.
