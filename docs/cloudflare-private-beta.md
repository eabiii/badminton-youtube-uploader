# Cloudflare private-beta runbook

Phase 3 uses one Cloudflare Worker with Static Assets, not a Pages project. Production is the existing `badminton-youtube-uploader` Worker; staging is its fixed Preview named `staging`. Each environment has its own APAC D1 database. Both publish to the dedicated YouTube test channel and Destination Playlist with `YOUTUBE_AUDIT_APPROVED=false`, so effective Visibility remains Private.

Login throttling permits five failed attempts per hashed client IP. Production uses a 15-minute window, while staging uses a one-minute window so accidental beta-testing lockouts clear quickly without disabling brute-force protection. The durations are configured through `LOGIN_RATE_LIMIT_WINDOW_SECONDS` in `wrangler.jsonc`.

- Production: `https://badminton-youtube-uploader.edbar1025.workers.dev`
- Staging: `https://staging-badminton-youtube-uploader.edbar1025.workers.dev`

## Resources and migrations

The D1 database identifiers in the Wrangler files are configuration, not secrets. Create missing resources in the intended Cloudflare account only once:

```sh
pnpm exec wrangler d1 create badminton-youtube-uploader-staging --location apac
pnpm exec wrangler d1 create badminton-youtube-uploader-production --location apac
```

Apply migrations before deploying application code, then verify that both lists report no pending migrations:

```sh
pnpm exec wrangler d1 migrations apply badminton-youtube-uploader-staging --remote --config wrangler.staging-migrations.jsonc
pnpm exec wrangler d1 migrations apply badminton-youtube-uploader-production --remote
pnpm exec wrangler d1 migrations list badminton-youtube-uploader-staging --remote --config wrangler.staging-migrations.jsonc
pnpm exec wrangler d1 migrations list badminton-youtube-uploader-production --remote
```

The account's `workers.dev` subdomain is `edbar1025`. Confirm it under **Workers & Pages → Overview** before changing account routing. Wrangler may return an empty `urls` list for the fixed Preview even when its conventional alias above is reachable, so probe the documented staging URL directly.

Create or update the fixed staging Preview after a successful build:

```sh
pnpm build
pnpm exec wrangler preview --name staging
```

## Secrets

Staging and production need all five declared secrets. Use a distinct shared password for each environment. Paste values only into Wrangler's interactive prompt; do not put values in arguments, files, shell history, logs, or GitHub workflow output.

Password hashes use PBKDF2-HMAC-SHA256 with 100,000 iterations, the maximum accepted by Cloudflare Workers Web Crypto. A hash generated by an older version of this repository with 600,000 iterations cannot be verified by the deployed Worker and must be regenerated.

Run the hash commands in an interactive terminal so the script can prompt for the password with echo disabled. Invoke the script with `node` rather than `pnpm password:hash`, because pnpm prints its script banner to standard output, which would be piped into the secret.

```sh
node scripts/hash-password.mjs | pnpm exec wrangler preview secret put SHARED_PASSWORD_HASH --name staging
pnpm exec wrangler preview secret put YOUTUBE_CLIENT_ID --name staging
pnpm exec wrangler preview secret put YOUTUBE_CLIENT_SECRET --name staging
pnpm exec wrangler preview secret put YOUTUBE_REFRESH_TOKEN --name staging
pnpm exec wrangler preview secret put YOUTUBE_PLAYLIST_ID --name staging

node scripts/hash-password.mjs | pnpm exec wrangler secret put SHARED_PASSWORD_HASH
pnpm exec wrangler secret put YOUTUBE_CLIENT_ID
pnpm exec wrangler secret put YOUTUBE_CLIENT_SECRET
pnpm exec wrangler secret put YOUTUBE_REFRESH_TOKEN
pnpm exec wrangler secret put YOUTUBE_PLAYLIST_ID
```

After the correctly named production refresh token is installed and staging validation passes, remove the obsolete typo:

```sh
pnpm exec wrangler secret delete YOUTUBE_REFRESH_TOKE
```

The unauthenticated `/api/health` route returns `200 {"status":"ok"}` only when runtime configuration is complete and D1 answers a trivial query. All failures return the same `503 {"status":"unavailable"}` response. The check does not call YouTube and does not expose binding values, secret names, database identifiers, or OAuth details.

## GitHub configuration

Create an account-scoped Cloudflare API token restricted to the intended account with `Workers Scripts: Edit` and `D1: Edit`; no zone permission is needed while using `workers.dev`. Add it and the account ID as GitHub repository secrets:

- `CLOUDFLARE_ACCOUNT_ID`
- `CLOUDFLARE_API_TOKEN`

The CI workflow verifies pull requests and `main`. Manual staging deployment accepts any selected branch. Manual production deployment runs only from `main`, records the previous deployment ID in its job summary, migrates, deploys, and probes health. Workflows derive the account's `workers.dev` subdomain from the Cloudflare API rather than storing it in the repository.

## Acceptance and rollout

Before production, exercise staging with two real browsers and verify:

- `/api/health` and `/` return `200`, while protected APIs return `401` without a session.
- Login persists, logout revokes the session, and `/api/session` reports live publishing with audit approval disabled.
- Five failed staging logins cause the next attempt to return `429` with `Retry-After`; login becomes available again after one minute.
- A real Private Game Upload larger than 64 MiB completes through multiple chunks and enters the Destination Playlist.
- A second browser cannot upload concurrently; cancellation and lease expiry release the lock.
- Retrying playlist insertion after Partial Success does not upload the video twice.
- Workers logs, browser storage, responses, built assets, and network traffic contain no OAuth credentials, refresh/access tokens, YouTube resumable-session URL, cookies, request bodies, or video data.
- PBKDF2 verification stays within the selected Workers CPU plan, and a near-2 GB upload completes reliably.

Deploy production manually and perform a small Private smoke upload. Then use Cloudflare's deployment rollback controls to restore the deployment ID recorded by the workflow and exercise D1 Time Travel recovery. Record evidence before checking the corresponding `PLAN.md` items; never mark an operational item complete based only on repository configuration.
